## 实现要点

- 加速 = 在 GitHub 域名 URL 前拼镜像前缀, 如 `https://v6.gh-proxy.org/https://github.com/...`
- Release 加速可**独立设置**: `release_proxy`(或 `GITX_RELEASE_PROXY`) 只作用于 `gitx release`
  与发布页链接, 解析链 `--proxy > GITX_RELEASE_PROXY > release_proxy > GITX_PROXY > proxy`;
  留空 = 跟随全局, 所以不设置时行为与旧版一致 —— 某个镜像对 API 限流时只需换 Release 那条链路。
- 拉取(克隆 / 下载 / Release 附件 / API)走加速; 推送走直连 —— 镜像对 `git push` 返回 405。
- 存在 URL 重写规则(全局或仓库本地 `--local`)时, 推送地址自动改用 SSH(gh 已配好密钥),
  避免 https 推送被规则重写到镜像。
- `gitx proxy install` 利用 git 自身的 `url.<镜像>/.insteadOf` 规则, 全局生效。
- 分支自动探测: `git ls-remote --symref` 取默认分支(main/master), 结果缓存 1 小时。
- 文件夹下载: 部分克隆 + 稀疏检出(`--filter=blob:none --sparse`), 检出时按需拉取目标目录的 blob。
- `gitx proxy auto` 用 `git ls-remote` 实测各加速源(含直连)克隆端点耗时, 选最快的。
- 命令分发: `gitx` 入口先走**只依赖标准库**的快速通道(git 透传 / `--version` / `--help`),
  其余交给 Typer 子命令; 首词像链接(`https://` / `git@`)、或形如 `owner/repo` 且本地没有
  同名路径, 就自动补 `download`(后者与 `github.parse_url` 的简写解析共用同一判断)。
  笔误提示只在 git 自己判定"不是 git 命令"(退出码 1)时补一句, 不多花一次探测子进程。
- 需要写权限或账号态的功能(`publish` / `actions` / `auth` / `repos` / `pr create`)全部交给
  已登录的 `gh`: gitx 只拼参数、不接触令牌, 前置检查(是否安装 / 是否登录)与 JSON 解析
  集中在 `ghcli.py` 一处。
- `gitx ignore` 复用 github/gitignore 官方模板库, 索引缓存 7 天, 按名拉取(raw 也走加速)。

### 守护进程 (`daemon.py`, 配置 `daemon = true` 才启用, 默认关)

低配机上 Python 每次都要重新导入 typer / rich (约 1-2 秒), 占了短命令的大半耗时。做法:

- 后台进程 (`python -m gitx daemon serve`) 先 `WARMUP` 导入重模块, 再在
  `~/.cache/gitx/daemon.sock` 上监听(**Unix 域套接字**, 不占端口、不监听网络);
- 客户端**通过 `SCM_RIGHTS` 把 stdin/stdout/stderr 传过去**, 所以选择器 / 确认 / 进度条 /
  终端配色都照常工作, 输出顺序不变;
- 每个请求 **fork 一个预热好的子进程**执行 (`cli.main`) —— fork 继承已导入的模块, 因此省掉
  重复导入, 同时保持进程隔离 (状态不互相污染, Ctrl+C 只影响当次);
- **环境变量与工作目录随请求发送** (守护进程可能是别的命令启的, 它的环境未必同一次);
- 协议是"先回 `{"pid"}`, 再回 `{"code"}`": 客户端据此把 SIGINT/SIGTERM/SIGHUP **转发**给那个
  pid —— 子进程在守护进程的会话里, 收不到终端的 SIGINT, 不转发的话交互式命令无法取消;
- 用 `flock(daemon.lock)` 保证同一时刻只有一个守护进程 (并发召唤时后来者安静退出),
  `serve` 进程带 `GITX_IN_DAEMON=1` 环境变量, 入口据此不再重复路由 (否则会套娃);
- 版本号不一致 (刚升级) / 连不上 / 平台不支持 → **静默回退本地执行**; 空闲 `daemon_idle` 秒
  自己退出, 不留常驻进程; 起不来的原因看 `~/.cache/gitx/daemon.log`。
- 配色联动: `palette = auto` 时, 开了守护进程就用**终端自己的 16 色调色板** (`TERMINAL_THEME`,
  ANSI 名而非 24 位 hex), 低配终端不必为真彩色付出渲染开销; `mocha` 可强制内置 Catppuccin。
  注意 ANSI 色名在 rich 与 prompt_toolkit 里**不是同一套** (rich 的 `bright_black` 在
  prompt_toolkit 里叫 `ansibrightblack`), 选择器用错会直接抛 `Wrong color format`。
- **子进程必须重建控制台** (`console.rebind()`): rich 在 `Console` 构造时就定死了
  "是否终端 / 多少列 / 支持几种颜色"。守护进程的 stdout 指向日志文件, 不重建的话 fork 出来的
  子进程即使换成了客户端终端也仍按"没有终端 + 80 列"渲染 —— 表现为掉色与折行。
- **别把"管守护进程自己"的命令交给守护进程执行**: `gitx daemon stop/restart` 若走路由, 守护进程
  单线程收请求会与子进程互相等待 (死锁)。因此 dispatch 用一条**零依赖快速通道**处理
  `daemon status/start/stop/restart` (只 import 标准库, 自己读 TOML、自己上色), typer 里只留
  `bench` 与 `serve`。控制类命令加 socket 超时兜底 (30 秒), 不允许出现"卡住不退"。
- **召唤失败要有冷却** (`daemon.fail`, 60 秒): 否则每条命令都要白等一次 spawn 超时。
- 效果要能被量出来: `gitx daemon bench` 用 `GITX_IN_DAEMON=1` (强制本地) 与正常走法各跑几轮取
  中位数。导入便宜的快盘机器上差距只有几百毫秒, 低配机 / 冷缓存 / 机械盘上差距才明显 —— 报数
  据时把这个前提一起说清。

### 缓存 (`cache.py`, 配置 `cache = true`, 默认开)

- 两类: 整文件缓存(`gitignore.json`, 由模块自己读写) 与**键值缓存**
  (`~/.cache/gitx/entries/<sha256 前 20 位>.json`, 统一走 `cache.get/put`);
- 目前接入: GitHub API 的**只读 GET 响应**(`github._request`, 默认 TTL `cache_ttl` = 300 秒;
  命中返回空响应头, 所以依赖 `Link` 头的 `api_count` 明确 `cache_ttl=0`)、远端默认分支探测(1 小时)。
  版本查询与发布列表走的就是 API 缓存, 因此不必单独接;
- 写操作后必须作废: `publish` 的创建 / 上传 / 更新 / 删除之后调用 `cache.flush()`
  (否则刚改完的发行版会读到旧数据);
- `repos` 的读出结果(列表 / 搜索 / 详情 / 分支)统一用 `ghrepo:` 前缀的键, 写操作后调
  `cache.drop_prefix("ghrepo:")` 只作废自己这一批, 不牵连 release 的 API 缓存; `--fresh`
  传进 fetch 层后既不吃缓存也不写缓存。实测 `repos list -n 3` 7.9s → 1.4s;
- 登录态判断(`ghcli.logged_in`)用 `gh auth token`(只读本地 hosts.yml, ~0.5s)而不是
  `gh auth status`(~3s 且每次都要校验凭据), 并在进程内缓存 —— `repos` 一条命令会问很多次;
- gh 的**布尔开关只认等号形式**(`--archived=true`): 写成 `--archived true` 会被当成查询词,
  静默返回空结果, 因此 `_search_args` 一律拼 `=`。
- 写入用 `临时文件 + replace` 原子替换, 损坏 / 过期 / 键不符一律当未命中;
- `gitx cache` / `list` / `prune` / `clear` 用来查看与清理; `cache = false` 整体旁路。

## 为什么快 (实测数字, 2026-10 经 v6.gh-proxy.org)

- **git 透传不加载 typer**: `gitx status` / `gitx --version` 由只依赖标准库的快速分发处理,
  从 ~2.5s 降到 ~0.6s(含 uv 与 python 启动, 低配机器上); 加速源列表也不再靠多语言输出的
  `git help -a` 猜测, 直接交给 git 自己执行。
- **文件夹下载快 8 倍**: `git/git` 的一个子目录, 纯稀疏检出 30.7s / 14 MB → 部分克隆
  (`--filter=blob:none --sparse`) 3.8s / 4.2 MB。只拉取目标目录的 blob。
- **源码包路线**: `-x` 走 API 的 `/tarball/<ref>`, 单个 HTTP 流, 不要 git 历史时比克隆省一整个
  git 握手与对象协商。
- **断点续传**: 大附件中断不再从头下; `.part` 与目标不符(416 / 大小对不上)时自动丢弃重来。
- **按需加载**: rich.progress / rich.prompt / urllib / shutil / questionary 全部用到才导入。
- 并行下载实测**没有收益**(镜像按连接限速, 4 路并发比单路还慢), 故不做 —— 有证据才动刀。

## 源码结构

```
src/gitx/
  __init__.py   入口: 快速分发 -> 守护进程 -> typer    dispatch.py   git 透传 / --version 快速通道 (仅标准库)
  console.py    rich 控制台 (Catppuccin / 终端配色两套主题)
  config.py     持久化配置 (~/.config/gitx/config.toml, TOML + 自动迁移旧 JSON)
  daemon.py     召唤式守护进程 (预加载 + fork 执行)     cache.py      缓存 (键值 TTL + 查看 / 清理)
  accel.py      加速源与测速                              gitcmd.py     git 命令封装 (前置检查/分支/推送/维护原语)
  github.py     URL 解析 + REST API 客户端 (token 复用, 只读响应走缓存)
  net.py        HTTP 下载: 断点续传 + 进度条              download.py   仓库/文件夹/源码包下载
  release.py    Release 附件 (API)                        upgrade.py    自更新
  repo.py       init / info / commit / diff / discard / clean / undo / graph / tidy / url
  branch.py     branch / switch / merge / rebase / fetch   sync.py       push / pull / sync
  stash.py      暂存       tag.py  标签       remote.py  远程       submodule.py  子模组
  hub.py        search / stat / web / ignore (交互式搜索在 cli.py)
  pr.py         Pull Request           ghcli.py  gh CLI 共用层 (publish / actions / auth / repos / pr 共用)
  actions.py    Actions 运行与工作流    auth.py   账号登录态     ghrepo.py  我的仓库 (挑/搜 -> 编辑界面)
```

## 开发与验证

```bash
uv run python -m gitx --help
uv run python -m gitx release cli/cli --list   # API + 加速 的实测例子
uv build --out-dir dist                         # 构建 sdist + wheel (发布用)
uvx ruff check src/gitx                         # 静态检查 (规则见 pyproject.toml 的 [tool.ruff])
```

约定:

- 行宽 130 (pyproject 里定), 注释与提示语一律中文, 全角标点是故意的(ruff 的 RUF001/002/003 已忽略)。
- 启动路径要保持"轻": 重依赖 (rich.progress / questionary / urllib / shutil / webbrowser)
  一律**用到才导入**, 别放到模块顶层; 新命令不要给 `gitx status` 这类透传路径加负担。
- 交互输出统一走 `console.py` 的语义化封装 (`info/step/done/warn/error/table/quicklist/select`),
  动态文本必须用 `txt()` 包住 (否则 `[]` 会被 rich 当样式标签)。
- 验证以"真跑一遍"为准: 改了哪条命令就跑哪条 (交互式命令用 pty 驱动),
  单测不是这个项目的证明方式; 提交前至少跑一次 `uv run python -m gitx doctor`。
- 版本管理与提交用 `jj` (仓库是 colocated: `.jj/` 与 `.git/` 并存), 写操作不要用 git 命令。
